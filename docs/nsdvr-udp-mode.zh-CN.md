# NSDVR UDP 模式设计（草案）

状态：设计稿，尚未实现。服务端改动在 NSDVR-server 分支上进行，与 [实验扩展协议](nsdvr-ext-protocol.zh-CN.md) 相互独立。

> **2026-10-11 评估：暂不实施，留作参考。** [音频压缩测试](https://github.com/onewilk/NSDVR-server/blob/nsdvr/reports/2026-10-11-audio-compression/README.zh-CN.md)
> 的数据显示：网络良好时游戏中几乎不丢帧，也没有发送卡顿；弱网下丢多少帧取决于串流码率超出链路容量多少，链路装得下时
> TCP 几乎不丢帧；马车 8 菜单页的周期性卡顿来自主机 CPU。这几种情况换成 UDP 都改善不了。降低码率（Opus 64k）在临界
> 链路上效果明显，优先级高于传输层改造。如果以后出现「链路容量足够但 TCP 仍然卡顿」的数据，再重新评估。

## 1. 目标与范围

在 SysDVR 现有的 USB、TCP Bridge、RTSP 之外新增第四种模式 **UDP**。和其他模式一样互斥：Switch 上同一时间只运行一种。

- **目标**：Wi‑Fi 下减少 TCP 的队头阻塞（一个包丢了，后面的数据全部等重传）和确认包对空口的占用，降低卡顿和断档。
- **不变**：画面仍是系统录像服务给的 720p30 H.264，码率不可调；音频沿用扩展的编码（PCM、24 kHz、ADPCM、Opus）。
- **不做**：拥塞控制和码率自适应（录像服务不提供参数）、多客户端、跨互联网传输。

单独成模式而不是在 TCP Bridge 里协商，是因为：TCP Bridge 的代码完全不动，后续维护成本更低；网络缓冲可以按模式配置，静态内存不增长（见 2.2）。

## 2. 服务端（sysmodule）

### 2.1 模式与入口

- 新增 `UDP_MODE`，和 `TCP_MODE`、`RTSP_MODE` 一样有自己的视频/音频线程和初始化、退出函数。
- 设置程序（SysDVR-conf）增加「UDP」选项和对应的 IPC 命令；开机默认模式文件 `/config/sysdvr/udp`。设置程序随本分支一起分发。
- 局域网广播沿用 19999 端口，信标里注明当前模式是 UDP，客户端据此提示「Switch 上选的是 UDP 模式」。

### 2.2 网络按模式初始化（静态内存零增长）

现在 SysDVR 开机时就用同一份配置初始化网络服务，借出 440KB 静态内存，所有模式（包括不联网的 USB）都一直占着。改为：

- 进入网络模式时初始化网络服务，退出模式时断开；借出的内存放进各模式共用的静态区（`StaticBuffers` 联合体），每个模式带自己的一份配置。
- 切换模式的顺序：停线程 → 断开网络服务 → 清零共用区 → 初始化新模式。

| 模式 | 网络配置（TCP 发送上限 / TCP 接收 / UDP 发送 / UDP 接收，×2） | 借出内存 | 模式自身缓冲 | 合计 |
|---|---|---|---|---|
| TCP Bridge | 200 / 8 / 8 / 4 KB | 440 KB | Opus 等 56 KB | **496 KB** |
| RTSP | 同上 | 440 KB | 28 KB | 468 KB |
| UDP | 16 / 8 / 16 / 16 KB | 112 KB | 重传缓存 + Opus ≤ 384 KB | ≤ 496 KB |

共用区按最大的模式预留，最大的仍是 TCP Bridge 的 496 KB，与现在（440 KB 网络缓冲 + 56 KB 共用区）相同，所以 **UDP 模式不增加静态内存**。重传缓存因此最多可以给到约 320 KB。

注意：这改变了官方 TCP Bridge、RTSP 的网络初始化时机，需要回归测试（反复切换模式、休眠唤醒、长时间串流）。

### 2.3 连接流程

1. 客户端通过广播或手动 IP 找到 Switch，用 **TCP 连接控制端口**（暂定 9933）做握手。握手沿用官方结构（协议 03 + 扩展字段），附带客户端的 UDP 端口、音频编码和发送节奏参数。
2. 客户端从自己的 UDP 端口向 Switch 的媒体端口（暂定 9934）发一个「打洞」包，Switch 以这个包的源地址作为发送目标，同时确认 UDP 双向可达。
3. Switch 把画面和声音都以 UDP 数据报发出。控制连接一直保持，用于控制消息（切换音频编码等）、诊断包和断开检测。
4. 控制连接断开或连续若干秒收不到客户端的保活包，即结束会话、回到等待连接。

### 2.4 数据报格式

所有数字为小端。数据报不超过 1428 字节（加 IP/UDP 头 28 字节，在 1500 的以太网 MTU 内，不触发 IP 分片）。

| 偏移 | 类型 | 含义 |
|---|---|---|
| 0 | u16 | 魔数 `0x4E55` |
| 2 | u8 | 版本 1 |
| 3 | u8 | 类型：1 画面，2 声音，3 缓存未命中（请求重传的包已被覆盖，负载为空） |
| 4 | u32 | 包序号（按类型各自递增，用来发现丢包） |
| 8 | u32 | 帧号（按类型各自递增） |
| 12 | u16 | 分片序号 |
| 14 | u16 | 分片总数 |
| 16 | u64 | 录像服务的时间戳（微秒） |
| 24 | u8 | 标志：关键帧、重放标记、多 NAL（含补发的 SPS/PPS） |
| 25 | u8 | 重放槽（同官方协议） |
| 26 | u16 | 本片负载长度（≤ 1400） |
| 28 | — | 负载 |

一帧画面按 1400 字节切片；静止画面去重、SPS/PPS 补发沿用 SysDVR 现有逻辑，只是改由数据报承载。

### 2.5 丢包恢复

- **重传请求（NACK）**：客户端发现包序号有缺口后，等一个很短的乱序窗口（约 3 ms），把缺的序号区间用 UDP 发回 Switch；重复请求无害。
- **重传缓存**：Switch 按包序号保留最近约 200～320 KB 的数据报；请求的包还在缓存里就补发，已经被覆盖就回一个「已不在缓存」应答，客户端立即放弃这一帧。
- **帧期限**：客户端对每一帧设一个最晚完成时间（与平滑缓冲的出帧时间对齐，再留少量余量）。到期还不完整就丢弃，按丢帧处理：定格到下一个关键帧。录像服务每 0.5 秒一个关键帧，所以最坏恢复时间是 0.5 秒。
- 局域网往返通常只有几毫秒，一次重传基本在下一帧到来前完成。前向纠错（XOR 冗余包）留作后续选项，视真机丢包形态再定。

### 2.6 发送节奏

一个关键帧可能拆成上百个数据报，一次性发出会被 Wi‑Fi 驱动队列丢掉或阻塞（这一层 SysDVR 改不了）。发送端用令牌桶控制节奏：

- 默认平均速率约 30 Mbps，突发额度约 16 KB；关键帧（约 100 KB）大约用 25 ms 发完。
- 速率、突发额度在握手里由客户端指定，便于真机调参；发送时遇到缓冲满就短暂让出 CPU 再试，并计数。

### 2.7 诊断

- 沿用扩展的诊断包（经控制连接发送），追加：发出的数据报数、发送缓冲满的次数、收到的重传请求数、补发数、缓存未命中数。
- 性能记录器照常记录 4 个核心占用和 SysDVR 线程 CPU，便于和 TCP Bridge 对比。

## 3. 客户端（NSDVR）

- 串流页新增第四个模式「UDP（实验）」。连接方式和 TCP Bridge 一样：局域网发现、手动 IP、最近连接。
- 新的原生数据源实现现有的 `StreamSource` 接口：收包、重组、NACK、帧期限，下游的关键帧缓存、丢帧定格、平滑、统计都不用改。
- 给 UDP 套接字也设置华为网络加速的数据流优先级。
- 统计浮层和 `stats.csv` 增加：丢包率、重传次数、超时丢弃的帧数。

## 4. 测试

- **电脑端**：主机模拟服务端（hostmock）增加 UDP 模式，用同一套可移植 C 代码；进程内注入随机丢包、突发丢包、乱序和抖动；端到端自测增加相应场景，统计送达帧率和延迟。
- **真机**：同一环境下交替使用 TCP Bridge 和 UDP 模式，对比丢帧率、卡顿、延迟，以及 3 号核心占用和内存（性能记录器）。

## 6. 风险

- Switch 网络栈对 UDP 突发的实际行为（丢弃还是阻塞、缓冲满的频率）未知，发送节奏参数需要真机实测。
- 网络按模式初始化改动了官方模式的初始化时机，有引入回归的风险。
- 部分路由器的隔离或防火墙可能挡 UDP，握手后的「打洞」包可以及早发现并提示用户改用 TCP Bridge。
- 设置程序需要随本分支一起安装，否则 Switch 上选不到 UDP 模式。
