# NSDVR extension test vectors (v1)

Generated by `NSDVR-server/host/build/next_vectors` (`make -C NSDVR-server/host vectors`) with exactly the
sysmodule's encoder code (`sysmodule/source/next/next_audio.c`, libopus 1.6.1 fixed point). Protocol:
`docs/nsdvr-ext-protocol.md`. All integers little endian, all PCM is s16le interleaved stereo.

## Input

- `input_48k_s16le_stereo.raw` (+ `input.wav`): 49152 frames = 1.024 s of `audio_eval/src/aliens_48k.wav`
  starting at 30.0 s. That is 12 grc captures with AudioBatching = 3 (4 x 1024 frames each).
- Capture n (0..11) has the grc timestamp `1000000 + round(n * 4096 * 1e6 / 48000)` microseconds.

## Per vector

- `<name>.stream.bin` – the exact bytes the server writes to the 9922 socket after the handshake:
  a sequence of `PacketHeader` (18 bytes: u32 magic 0xCCCCCCCC, u32 DataSize, u64 Timestamp, u8 MetaData,
  u8 ReplaySlot) + DataSize payload bytes. Feed it to the client's packet parser as is.
- `<name>.packets.tsv` – one line per packet: byte offset in the stream, header fields and the parsed
  ExtAudioHeader. `encode_us` is 0 in the vectors (the real server fills in the measured time).
- Expected decoder output (only for single-codec vectors):
  - `pcm24.expected_24k_s16le_stereo.raw` – the 24 kHz samples, i.e. the concatenated packet bodies.
    Bit exact: this is what any correct parser must produce.
    `pcm24.ref_up48_s16le_stereo.raw` – for reference only: 48 kHz output of the offline evaluation's
    upsampler (`up48()` in tools/audio_codec_eval.py: zero-stuffing, gain 2, 127-tap low-pass at 11.5 kHz,
    centered). The client may use a different upsampler; compare with a tolerance.
  - `adpcm.expected_48k_s16le_stereo.raw` – bit exact IMA ADPCM decode (every packet decoded from its own
    8-byte state header; the result is identical to decoding the whole stream continuously).
  - `opus_*.ref_decoded_48k_s16le_stereo.raw` – libopus 1.6.1 (fixed point) `opus_decode()` of every frame
    in order with one decoder. Another Opus decoder (float libopus, platform codec) will differ slightly:
    compare with a tolerance (e.g. SNR against this file > 40 dB, or after aligning, max abs diff of a few LSB).
    Note the Opus encoder delay: decoded sample k corresponds to input sample k - 120 (2.5 ms).
  - `pcm48.expected_48k_s16le_stereo.raw` – identical to the input.
- `switch.*` – control messages applied between packets (PCM24 -> ADPCM -> Opus 96k/20ms -> Opus 32k/10ms
  (live change, no reset) -> PCM48 -> Opus 64k/20ms c10). Tests the dispatcher: codec marker changes,
  dropped Opus carry on codec switches (< 20 ms), timestamps. No expected decode file: decode per packet.

## Packet facts worth testing

- ReplaySlot is 0xE0 | codec on every extension audio packet; MetaData is 0x06 (audio | data).
- PCM24/ADPCM: one packet per capture, `samples_per_channel` = 2048 (PCM24, 24 kHz) / 4096 (ADPCM).
- Opus: frames are cut from a continuous stream, so a packet holds 4 or 5 frames (20 ms) or 8 or 9
  (10 ms); the remainder (< 1 frame) is carried into the next packet. The packet timestamp is the
  time of the first sample of its first frame, so timestamps are continuous: next = ts + spc * 1e6 / 48000
  (+-1 us rounding).
- Opus is constant bitrate: every frame is exactly kbps * frame_samples / 384 bytes (240 bytes at 96 kbps / 20 ms).

## Control message / handshake bytes (hex)

- Handshake, audio channel, AudioBatching 3, ext flag, Opus 96 kbps complexity 5 20 ms, TOS:
  `AA AA AA AA 30 33 02 00 03 04 03 30 05 02 00 00`
- Handshake, video channel, NAL hash + SPS/PPS injection, ext flag, diagnostics + TOS:
  `AA AA AA AA 30 33 01 07 00 04 00 00 00 03 00 00`
- Control message: switch to Opus 64 kbps, complexity 10, 10 ms frames: `53 44 56 58 03 20 1A 00`
- Control message: switch to ADPCM: `53 44 56 58 02 00 00 00`

`manifest.json` lists every file with sizes and frame counts.
